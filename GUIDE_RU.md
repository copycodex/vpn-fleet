# Гайд: парк VPN с нуля

Путь от пустой машины до работающей ноды, шаг за шагом. README — справочник:
он описывает, что где лежит и почему. Здесь — порядок действий и ожидаемый
результат каждого.

Гайд ведёт один и тот же пример: нода, купленная у провайдера VPS, которую
отдали с паролем на первый вход. Подставляй своё имя ноды везде, где написано
`<node>`.

## Визардом или руками

Каждый шаг ниже умеет визард, и каждый можно сделать руками — это не два разных
порядка, а один и тот же. Визард ничего не прячет: он лишь набирает те же файлы
и зовёт те же команды, а гайд объясняет, что именно и почему.

Один вход на всё:

```bash
wizard/wizard.py
```

Он смотрит, что уже сделано, называет стадию каждого сервера и предлагает
следующий шаг — но не выполняет его без твоего «да». Своей памяти у него нет:
стадия выводится из файлов и состояния двери прямо сейчас, поэтому прерванный
прогон продолжается с того места, где встал.

Экран собран из трёх частей:

```
KEYS:
  установка  my-fleet
  age        ~/.config/sops/age/my-fleet.txt
  ssh        ~/.ssh/my-fleet_ed25519

MENU:
  1) Create server
  2) Servers
  3) Quit

YOUR CHOSE [1]:
```

`KEYS` печатается всегда: это первое, что надо узнать, садясь за забытую
машину. Блок `WARNINGS` появляется, только когда чего-то не хватает, и каждая
строка в нём несёт команду, которой это чинится, — когда всё на месте, блока
нет вовсе. Ответы везде только цифрами: `Back` и `Quit` такие же пункты списка,
как остальные, и шаг назад есть из любого меню.

`Create server` ведёт сначала на выбор хостера — от него зависят и маршрут, и
дверь, поэтому он спрашивается раньше, чем что-то создаётся. `Servers` — список
заведённых с их стадиями; выбрав сервер, увидишь его следующий шаг и сможешь
запустить его отсюда.

Отдельные шаги, если идёшь по одному:

| Шаг | Командой | Руками — раздел |
|---|---|---|
| 0. Зависимости | `wizard/deps.sh` | 0.1–0.2 |
| 1. Ключи установки | `wizard/keys.sh` | 0.3–0.4 |
| 2. Частное дерево | `wizard/private_tree.py` | 0.5 |
| 3–9. Хостер и сервер | `make new-server` | 0.5, «Что дальше» |
| 10. Прогон | `make first-contact`, `make bootstrap` | «Что дальше» |

## Что понадобится

| Что | Зачем |
|---|---|
| Control host на Linux | с него идут все команды; на ноду руками не ходим |
| VPS с Ubuntu 22.04/24.04/26.04 | сама нода; покупается в панели провайдера |
| Первый вход к ней | пользователь, порт и пароль — то, что прислал провайдер |
| Консоль провайдера | запасная дверь, если сеть отвалится |

Terraform не нужен: он в репозитории есть, но написан под Hetzner. Нода у
любого другого провайдера создаётся в его панели, а дальше всё делает Ansible.

## Шаг 0. Control host с нуля

Исходное состояние: чистая машина. Ни `sops`, ни `age`, ни ключей парка нет.

**0.1.** Клонируем репозиторий, работаем из его корня.

**0.2.** Ставим инструменты: apt-пакеты (git, python3, venv, ssh, age) →
`sops` релизным бинарём 3.9.1 → python-зависимости из `requirements-ci.txt`
в venv → коллекции ansible. Проверка: три команды печатают версии.

**0.3.** Генерим age-ключ в `~/.config/sops/age/<установка>.txt`, chmod 600,
забираем публичную часть `age1…`. Бэкап вне машины.

**0.4.** Генерим SSH-ключ админа `~/.ssh/<установка>_ed25519`, без passphrase.

**0.5.** Заводим частное дерево в `private/`:

- `.sops.yaml` — свой age-получатель в оба правила;
- `ssh_keys.yml` — свой публичный SSH-ключ;
- `known_hosts` — пустой, ключи примет первое касание;
- `first-entry.sops.yml` — пустая карта `first_entry: {}`;
- `nodes/<node>.yml` и `secrets.sops.yml` — появляются вместе с первым
  сервером (`make new-server`).

**0.6.** `scripts/check-private-inputs.sh <node>` — красный только на
`known_hosts`, это норма до первого касания.

Итог: инструменты стоят, два ключа созданы, частное дерево заполнено, нода
готова к `make first-contact`.

Пункты 0.1–0.2 делает `wizard/deps.sh`, 0.3–0.4 — `wizard/keys.sh`,
0.5 — `wizard/private_tree.py`. Дальше разберём каждый элемент подробно: и
чтобы сделать руками, и чтобы понимать, что делает команда.

### 0.1. Репозиторий

```bash
git clone <url репозитория> vpn-fleet
cd vpn-fleet
```

Все команды ниже запускаются из корня репозитория, и это не вкус: `ansible.cfg`
объявляет инвентарь относительным путём `private/inventories`, там же лежит
`known_hosts`, а `Makefile` строит от корня все остальные пути. Из другого
каталога команды просто не найдут ни инвентаря, ни ключей.

В клоне частного репозитория `private/` уже содержит tracked-файлы установки:
правила SOPS, зашифрованные карты, инвентарь и known hosts. Перед шагом 0.5
проверь их; `wizard/private_tree.py` и образцы из `inventories/` нужны для
недостающих входов. В публичном экспорте этого дерева нет. Закрытые ключи
остаются вне Git.

### 0.2. Инструменты

Командой: `wizard/deps.sh` — он покажет таблицу «есть/нет», спросит один раз и
поставит только недостающее; `wizard/deps.sh --check` ничего не ставит вовсе.
Ниже то же самое руками.

Системные пакеты (Debian/Ubuntu):

```bash
sudo apt update
sudo apt install -y git python3 python3-venv python3-pip openssh-client age
```

Здесь ничего лишнего: `openssh-client` даёт `ssh`, `ssh-keygen` и `ssh-keyscan`
— три команды, которыми первый вход принимает host key и открывает дверь; `age`
даёт `age-keygen` для ключа шифрования; `python3-venv` нужен, чтобы поставить
ansible, не ломая системный Python.

`sops` — то, чем шифруются и правятся файлы с секретами: он держит значения
шифротекстом прямо в YAML, поэтому файл остаётся читаемым и диффится в git.
В репозиториях дистрибутивов он обычно старый или отсутствует, поэтому
ставится релизным бинарём. Версия файлов парка — 3.9.x:

```bash
curl -fsSL -o /tmp/sops \
  https://github.com/getsops/sops/releases/download/v3.9.1/sops-v3.9.1.linux.amd64
sudo install -m 0755 /tmp/sops /usr/local/bin/sops
sops --version
```

Python-зависимости пиннуты `requirements-ci.txt`. Каждая отвечает за своё:
`ansible-core` — движок, которым идут все шаги после первого входа; `pexpect`
ведёт PTY-диалог смены пароля на шаге 1; `PyYAML` читает карту первого входа;
`yamllint` и `ansible-lint` — локальные гейты, те же, что в CI. Ставь их в
venv: системный Python в свежих Ubuntu запрещает установку в себя.

```bash
python3 -m venv ~/.venv/vpn-fleet
~/.venv/vpn-fleet/bin/pip install -r requirements-ci.txt
source ~/.venv/vpn-fleet/bin/activate
ansible-galaxy collection install -r requirements.yml
```

`source` включает venv в текущей сессии терминала — в новой сессии его нужно
повторить. `ansible-galaxy` доставляет коллекции из `requirements.yml`:
`ansible.posix` и `community.general` дают модули ролям, а `community.sops`
учит ansible расшифровывать секреты прямо при чтении инвентаря, без ручного
`sops -d`.

Проверка шага — три команды должны отработать без ошибок:

```bash
sops --version
ansible --version | head -1
python3 -c 'import pexpect, yaml; print("deps ok")'
```

### 0.3. age identity — корень всего шифрования

Командой: `wizard/keys.sh` — он покажет уже имеющиеся ключи, предложит взять
существующий или завести новый и спросит имя установки. Ниже то же руками.

Ключей на всю установку ровно два, и зовутся они по её имени — ниже в примерах
это `vpn-fleet-01`. Имя установки с именем сервера не связано: серверов может
быть сколько угодно, они называются в 0.5 и живут в инвентаре, а age-ключ
шифрует частное дерево целиком и потому один.

```bash
mkdir -p ~/.config/sops/age
age-keygen -o ~/.config/sops/age/vpn-fleet-01.txt
chmod 600 ~/.config/sops/age/vpn-fleet-01.txt
age-keygen -y ~/.config/sops/age/vpn-fleet-01.txt    # публичная часть, age1…
```

`age-keygen -o` пишет приватную часть в файл, `age-keygen -y` печатает из неё
публичную — ту самую строку `age1…`, которой шифруются файлы парка. Приватной
частью они расшифровываются, и другой копии у неё нет.

Имя нигде не зашито. `Makefile` находит ключ сам: если в
`~/.config/sops/age` лежит ровно один `*.txt`, берётся он — тогда никаких
переменных писать не нужно. Появится второй ключ — назови нужный явно:
`make <target> FLEET=vpn-fleet-01`. Совсем другой путь задаётся так:
`make <target> SOPS_AGE_KEY_FILE=<path>`.

Приватная часть не коммитится никогда и не показывается на экране. Сделай
резервную копию вне машины: потеря ключа — потеря всех секретов парка.
Публичная часть (`age1…`) — получатель шифрования, она пойдёт в `.sops.yaml`.

### 0.4. SSH-ключ админа

```bash
ssh-keygen -t ed25519 -f ~/.ssh/vpn-fleet-01_ed25519 -C "vpn-fleet-01"
```

Имя то же, что у age-ключа: два ключа на установку, а не на сервер — этим
ключом открываются все ноды. Работает он обеими половинами: публичную (`.pub`)
первый вход кладёт на ноду в `authorized_keys`, приватной потом ходят и он сам,
и все запуски Ansible.
Поэтому путь к приватной половине объявляется в файле ноды
(`ansible_ssh_private_key_file`), а публичная попадает ещё и в список админов
в 0.5.

Проще всего сделать ключ без passphrase: первый вход идёт неинтерактивно и
спросить её не у кого. Если passphrase нужен — держи ключ в `ssh-agent`, а
`.pub` рядом с приватным.

### 0.5. Частное дерево

Командой: `wizard/private_tree.py` — он создаёт недостающее и дозаполняет
пустое, а чужого не трогает: плейсхолдер получателя предложит заменить, чужого
получателя не тронет вовсе. Ниже то же руками.

Четыре файла плюс каталог инвентарей. Каталог `private/` целиком вне публичной
части репозитория, поэтому в свежем клоне его нет — он появляется здесь.

```text
private/
├── .sops.yaml                                  правила шифрования
└── inventories/
    ├── first-entry.sops.yml                    карта первого входа
    ├── nodes/<node>.yml                        координаты ноды
    └── group_vars/all/
        ├── ssh_keys.yml                        публичные ключи админов
        └── secrets.sops.yml                    секреты парка
```

`private/inventories/known_hosts` заполнять не нужно: host key туда кладёт
первый вход в формате `<host> ssh-ed25519 <key> vpn-fleet:<node>:door`
(или `[<host>]:<port>` для другого порта). Бутстрап пишет подтверждённый
steady-порт с `vpn-fleet:<node>:steady`. Старым строкам без метки её можно
присвоить через «Fill in missing data»: визард покажет план и спросит перед
записью. Общий адрес требует решения человека.

**Правила шифрования — `private/.sops.yaml`.** Открой и подставь в оба правила
свою публичную часть age из 0.3:

```yaml
creation_rules:
  - path_regex: inventories/group_vars/all/secrets\.sops\.yml$
    age: age1…твой публичный получатель…

  - path_regex: inventories/first-entry\.sops\.yml$
    age: age1…твой публичный получатель…
    encrypted_regex: '^(password)$'
```

Правила два, потому что файлы шифруются по-разному: секреты целиком, а карта
первого входа — только по полю `password`, чтобы `user`, `port` и `method`
читались без ключа расшифровки.

Публичный `.sops.yaml` в корне репозитория остаётся образцом с плейсхолдером:
настоящего получателя в публичной части быть не должно.

**Инвентарь ноды.** Здесь появляется имя сервера — то самое, которым он будет
зваться везде дальше: в инвентаре, в префиксах секретов, в картах и во всех
командах. Бери говорящее, например `vpn-example-01`. Заготовки на конкретную ноду
нет и быть не может — имя и адрес знаешь только ты:

```bash
make new-server
```

Команда спрашивает имя, адрес и дверь, после чего пишет
`private/inventories/nodes/<node>.yml` с путём к ключу установки. Ничего уже
существующего она не трогает: заведённый сервер она дозаполняет.

Руками то же самое — копия `inventories/nodes/example.yml.template` с правкой
`ansible_host`, `node_name` и `ansible_ssh_private_key_file`. Первого входа в
этом файле нет и быть не должно: он живёт одной картой на весь парк.

**Ключи админов — `ssh_keys.yml`.** Список в образце пуст. Впиши свой ключ
установки:

```yaml
ssh_authorized_keys_devops:
  - name: control-host
    pubkey: "ssh-ed25519 AAAA… vpn-fleet-01"
```

Список обязан содержать ключ установки. Бутстрап ставит пользователю `devops`
ровно этот список и отключает root и пароль: пустой или чужой список оставит
ноду без единой двери.

**Секреты — `secrets.sops.yml`.** Этот файл заводит `make new-server` вместе с
первым сервером: `sops` отказывается шифровать документ без данных, поэтому
пустым он существовать не может. Визард создаёт пару X25519 Reality и short ID,
в том числе при дозаполнении сервера, когда все три поля отсутствуют. Частичную
тройку он отвергает, чтобы не ротировать существующую identity. При ручном
создании берут `inventories/group_vars/all/secrets.sops.yml.example`, меняют
префикс `node_example_` на имя ноды и заполняют согласованную тройку:

```yaml
node_<node>_reality_private_key: "<закрытый ключ Xray>"
node_<node>_reality_public_key: "<соответствующий открытый ключ Xray>"
node_<node>_reality_short_id: "<16 строчных шестнадцатеричных символов>"
node_<node>_clients: []
node_<node>_console_password: ""
```

Заполненный файл шифруется один раз, дальше он правится только через
`make secrets-edit`:

```bash
python3 scripts/secrets_lock.py private/inventories/group_vars/all/secrets.sops.yml -- \
  sops --config private/.sops.yaml -e -i \
  private/inventories/group_vars/all/secrets.sops.yml
```

Строка `node_<node>_console_password: ""` обязана существовать заранее: первый
вход её заменяет, а не создаёт. Пустое значение sops не шифрует — так видно,
что оно ещё не заполнено. UUID клиентов добавляются при создании клиентов;
Reality identity визард заводит до деплоя.

**Карта первого входа — `first-entry.sops.yml`.** Одна запись на ноду;
`user`, `port` и `method` — то, что прислал провайдер:

```yaml
first_entry:
    <node>:
        user: ubuntu
        port: 22
        method: password
        password: ""
```

`method: key` — для нод, которым провайдер положил ключ при создании; у такой
записи поля `password` нет вовсе. Заполненную карту шифруем той же командой:

```bash
python3 scripts/secrets_lock.py private/inventories/first-entry.sops.yml -- \
  sops --config private/.sops.yaml -e -i private/inventories/first-entry.sops.yml
```

Пароль вписывается последним, уже в шифротекст:

```bash
make secrets-edit FILE=private/inventories/first-entry.sops.yml
```

Редактор покажет файл расшифрованным — это единственный момент, когда пароль
виден на экране. После сохранения он ляжет в файл шифротекстом, а `user`,
`port` и комментарии останутся открытыми.

### 0.6. Проверка шага

```bash
scripts/check-private-inputs.sh <node>
```

Это гейт, а не отчёт: пока частные входы не заполнены, сетевые шаги не
начинаются. Он проверяет, что файлы на месте, что в `.sops.yaml` стоит
настоящий получатель, а не плейсхолдер, что список админских ключей не пуст,
что в секретах есть переменные с префиксом твоей ноды, и что дверь ноды
определена — есть запись в карте первого входа либо читается ключ парка.

Скрипт называет имя поля и файл, но никогда — значение. На этом шаге он ещё
красный одной строкой: `known_hosts` пуст, потому что host key ноды примет
первый вход. Всё остальное должно быть заполнено; `make doctor NODE=<node>`
станет полностью зелёным после шага 1.

## Что дальше

Сервер заводится одной командой — она и спрашивает всё остальное:

```bash
make new-server
```

Это шаги 3–9: хостер и его маршрут, имя и адрес, дверь первого входа, порт
после бутстрапа, транспорты, клиенты. В конце визард показывает план и ждёт
подтверждения: до «да» ни один файл не меняется.

**Хостер выбирает маршрут, и маршрута два.** У OVH и HostHatch ноду создаёшь
руками в панели, а дверь приходит письмом. У Hetzner ноды нет вовсе, пока её не
создал terraform: он же кладёт внутрь наш публичный ключ, поэтому пароля не
существует, дверь всегда `key`, а адрес появляется только в выводе terraform.
Каталог профилей — `inventories/hosters.yml`, новый хостер добавляется
`wizard/hoster.py --add`.

Дальше по порядку:

| Шаг | Команда | Что делает |
|---|---|---|
| 1. Первое касание | `make first-contact NODE=<node>` | принимает host key по TOFU, меняет выданный пароль, кладёт ключ парка, доказывает вход им и гасит запись в карте |
| 2. Бутстрап | `make bootstrap NODE=<node> FROM=<user>@<port>` | предполёт, затем `devops`, переезд SSH на выбранный порт, отключение root и пароля |
| 3. Нода | `make site NODE=<node>` | hardening, firewall по объявленным транспортам, Xray и sing-box |
| 4. Клиенты | `make add-client NAME=<client>`, `make export` | UUID в шифротекст, конфиг, ссылка и QR |

`FROM` у бутстрапа — та дверь, которую оставил первый вход: его запись в карте
после успеха удалена, поэтому пользователь и порт называются вызовом. Предполёт
проверяет четыре вещи до любого сетевого действия: касание пройдено, наш ключ
есть в списке админов, host key нового порта известен или будет записан, а сам
порт на ноде никем не занят.

Шаги 1–4 расписываются следующими разделами этого гайда.
